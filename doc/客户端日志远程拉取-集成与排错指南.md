# 客户端日志远程拉取 — 三端集成与排错指南

> 范围：`FitCoachServer/fitcoach-log` × `FitCoachRN/android/app/src/main/java/com/fitcoachrn/logger` × `FitCoachAdminManager/src/pages/tools/Logs`
>
> 目标：admin 后台输入用户 uid → 创建任务 → 客户端 120s 轮询 → 命中后打包 zip 上传 → admin 下载 zip 拿到 RN/JS + Android Native 双层完整日志。
>
> 配套技术文档：
> - 服务端：`FitCoachServer/fitcoach-log/doc/log技术文档.md`
> - 客户端：`FitCoachRN/android/app/src/main/java/com/fitcoachrn/logger/doc/logger技术文档.md`

关键设计要点（贯穿三端）：

| 维度 | 决策 | 出处 |
|------|------|------|
| RN/JS 与 Native 日志同源 | JS 走 bridge → 同一个 FileLogWriter，时序连续 | RN [`LoggerModule`](../../FitCoachRN/android/app/src/main/java/com/fitcoachrn/logger/bridge/LoggerModule.kt) |
| 客户端轮询周期 | 120s（OneTimeWork + 自我重排，绕开 PeriodicWork 15min 下限） | RN [`LogPullScheduler`](../../FitCoachRN/android/app/src/main/java/com/fitcoachrn/logger/pull/LogPullScheduler.kt) |
| 任务分配并发安全 | PESSIMISTIC_WRITE 行锁 + 状态机 PENDING→ASSIGNED→UPLOADING | Server [`LogPullTaskRepository.lockTopPendingForUid`](../fitcoach-log/src/main/java/com/lanprojects/fitcoach/log/repository/LogPullTaskRepository.java:36-51) |
| 上传幂等 | UPLOADED 直接返成功；UPLOADING 才落盘流转 | Server [`LogPullService.acceptUpload`](../fitcoach-log/src/main/java/com/lanprojects/fitcoach/log/service/LogPullService.java:198-249) |
| 防重复上传双保险 | 服务端状态机 + 客户端 LogProcessedStore（FIFO 100） | RN [`LogProcessedStore`](../../FitCoachRN/android/app/src/main/java/com/fitcoachrn/logger/pull/LogProcessedStore.kt) |
| 包大小硬上限 | 客户端打包 50MB / 服务端 multipart 60MB | yml [`log-pull.max-upload-size-bytes`](../fitcoach-app/src/main/resources/application.yml) |
| 文件保留 | UPLOADED zip 保留 7 天，scheduler 自动清盘 | Server [`LogTaskScheduler`](../fitcoach-log/src/main/java/com/lanprojects/fitcoach/log/service/LogTaskScheduler.java) |
| 下载文件名 | 服务端给建议名 `fitcoach_log_{uid}_{taskId}.zip` | Server [`AdminLogController.download`](../fitcoach-log/src/main/java/com/lanprojects/fitcoach/log/controller/AdminLogController.java:96-128) |

## 2. 接口契约一览

### 2.1 Admin 端（前缀 `/api/admin/logs/tasks`，需 admin token）

| Method | Path | 入参 | 返回 | 说明 |
|--------|------|------|------|------|
| POST | `/` | `CreateLogTaskRequest{ uid, remark?, recentHours? }` | `LogTaskDto` | 创建 PENDING 任务；同 uid 24h 内并发上限 1 |
| GET  | `/?uid=X&status=&page=1&size=20` | query | `PageVO<LogTaskDto>` | 必须按 uid 查 |
| GET  | `/{id}` | path | `LogTaskDto` | 详情 |
| GET  | `/{id}/download` | path | `application/zip` (blob) | 必须 status=UPLOADED；走 `FileSystemResource` 流式 |
| DELETE | `/{id}` | path | `Void` | 同步删 zip 文件 |

`LogTaskDto` 时间字段为 ISO 字符串（如 `"2025-01-15T12:34:56"`），前端 dayjs 解析。

### 2.2 客户端（需用户 access token）

| Method | Path | 入参 | 返回 | 说明 |
|--------|------|------|------|------|
| GET  | `/api/client/poll` | header Authorization | `Map<String,Object>`，含 `logTask` / `serverTime` 等 | 通用轮询入口；命中即把任务原子改为 UPLOADING |
| POST | `/api/logs/upload` | multipart `file` (zip) + `taskId` | `UploadLogResponse` | 幂等；超 50MB 拒收 |
| POST | `/api/logs/tasks/{id}/fail` | json `{reason}` | `LogTaskDto` | 客户端主动报错；触发重试或 FAILED_TERMINAL |

> 旧的 `GET /api/logs/pending` 已下线；拉取 PENDING 任务合并到通用轮询入口 `/api/client/poll`，
> 由 fitcoach-clientbus 模块统一鉴权 + 心跳，并通过 SPI 聚合各业务模块的"待办"。

`/api/client/poll` 响应示例（命中日志任务）：

```json
{
  "code": 0,
  "data": {
    "logTask": {
      "taskId": 123,
      "recentHours": 24,
      "expireAtMillis": 1704096000000,
      "uploadingDeadlineMillis": 1704009600000
    },
    "serverTime": 1717000000000
  }
}
```

未命中：`data` 中不出现 `logTask` 字段（只有 `serverTime`）。客户端用 `data.logTask ?? null` 处理即可。

`logTask` 内字段（即原 `PendingTaskDto`）：
- `taskId` Long — 上传时必须原样回传
- `recentHours` Integer/null — 客户端按 `createdAt >= now - recentHours` 过滤；null = 全量
- `expireAtMillis` long — 任务硬过期时间，超过这个时间上传也会被拒
- `uploadingDeadlineMillis` long — 当前 UPLOADING 阶段超时阈值；客户端可作为"应该在这之前上传完"的提示

### 2.3 错误码表（7301-7399）

| code | 含义 | 客户端是否 retry | 触发路径 |
|------|------|------------------|----------|
| 7301 | 任务不存在 | ✗ TERMINAL | upload 时 taskId 在 server 已被删除 |
| 7302 | 状态值不合法 | ✗ TERMINAL | 兜底，正常不应触发 |
| 7303 | 目标用户不存在 | — | admin 端创建时校验 |
| 7304 | 24h 内已存在未完成任务 | — | admin 端创建时去重 |
| 7305 | 任务尚未上传完成，不可下载 | — | admin 下载误选未完成任务 |
| 7306 | 日志文件已被清理 | — | 7 天保留期外 admin 仍点下载 |
| 7307 | 上传重试已达上限 | ✗ TERMINAL | 服务端把 status 标 FAILED_TERMINAL |
| 7308 | 任务已被其他设备/进程领取 | ✓ 下次轮询 | 同账号多端竞争 |
| 7311 | 上传文件为空 | ✗ TERMINAL | 客户端打包 BUG |
| 7312 | 文件过大 (>50MB) | ✗ TERMINAL | 应在客户端打包前裁剪 |
| 7313 | ContentType 不是 zip | ✗ TERMINAL | 客户端 multipart 写错 |
| 7314 | taskId 归属用户不匹配 | ✗ TERMINAL | uid 串改 / token 串号 |
| 7315 | 任务状态不允许上传 | ✗ TERMINAL | 二次上传同一任务 |
| 7316 | 服务端落盘失败 | ✓ retry 一次 | 磁盘满 / 权限不足 |
| 7321 | 任务已过期 | ✗ TERMINAL | 客户端超过 expireAt 才上传 |
| 7322 | 文件读取失败 | — | admin 下载时 IO 异常 |

> 客户端 TERMINAL 列表（出现这些不再 retry，记录原因后下次轮询不重新上传）：
> `{ 7301, 7307, 7311, 7312, 7313, 7314, 7315, 7321 }`
> 见 [`LogPullWorker`](../../FitCoachRN/android/app/src/main/java/com/fitcoachrn/logger/pull/LogPullWorker.kt) 中的 `TERMINAL_BIZ_CODES`。

## 3. 部署提示（生产 / 联调环境）

### 3.1 服务端 yml 关键项

```yaml
spring.servlet.multipart:
  max-file-size: 60MB
  max-request-size: 60MB

upload.base-dir: ${UPLOAD_BASE_DIR:./uploads}     # 日志 zip 物理落点 = {base-dir}/{log-pull.sub-dir}/{uid}/

log-pull:
  sub-dir: logs                # 默认 ./uploads/logs/{uid}/{filename}.zip
  max-upload-size-bytes: 52428800   # 50MB
  pending-expire-hours: 24
  uploading-timeout-minutes: 5
  uploaded-retention-days: 7
  max-retry-count: 3
  scheduler-interval-seconds: 60
  max-active-task-per-uid-in-24h: 1
```

部署前 checklist：

1. **磁盘容量** — 100 个用户 × 50MB × 7 天 = 35GB；UPLOAD_BASE_DIR 必须挂在有足够空间的卷上。
2. **文件清理** — 服务端 [`LogTaskScheduler`](../fitcoach-log/src/main/java/com/lanprojects/fitcoach/log/service/LogTaskScheduler.java) 每 60s 一轮自动清；如关闭 scheduler，需运维手动 cron。
3. **multipart 临时目录** — Tomcat 默认在 `${java.io.tmpdir}`；上传 50MB 时短暂占用，注意 `/tmp` 容量。
4. **反代** — 如果走 nginx，记得 `client_max_body_size 60m;`，否则 RN 上传会被 413 截断。
5. **时区** — 服务端使用 `LocalDateTime`，建议 JVM `-Duser.timezone=Asia/Shanghai`；前端展示用 dayjs，受浏览器时区影响。

### 3.2 客户端（FitCoachRN Android）

1. **Manifest 权限** — `INTERNET` 已具备；本模块不需要存储权限（写到应用私有 `getFilesDir()`）。
2. **WorkManager** — 已通过 `androidx.work:work-runtime-ktx:2.9.1` 引入，`MainApplication.onCreate` 会走 `LogPullScheduler.start()` 自动调度。
3. **登录态联动** — 用户登录/登出时，[`userManager.ts`](../../FitCoachRN/src/common/user/userManager.ts) 已经把 access token + uid 同步到 SharedPreferences；Worker 通过 SP 读取，不依赖 RN bridge。
4. **首次安装** — 应用冷启动 → 5s 后第一次轮询；之后每 120s 一次。后台进程被 OEM 杀掉的情况下，只要 App 再次冷启就会续上。
5. **观察点** — `adb logcat -s FCLogger:V FCLog/Worker:V` 可以看 native 端的 ENQUEUE / pending 命中 / 上传结果。

### 3.3 AdminManager

1. **构建时** — `pnpm build` 出 dist；`@/api/logs` 已被打入 main bundle，无 lazy chunk 风险。
2. **下载跨域** — 下载走 axios + blob，受同源策略限制；生产环境需保证 admin 域名与 `/api/...` 同源（一般同 nginx 反代）。
3. **角色** — VIEWER 可看不可创建/删除；底层 server 拦截器再兜一层（写权限 7003），UI 失败时会用 `ApiError.message` toast。

## 4. 排错指南

### 4.1 怎么看 zip 里的双层日志

zip 解压后的目录：

```
fitcoach_log_{uid}_{taskId}/
└── logs/
    ├── fitcoach-2025-01-15-1.log    ← 最早
    ├── fitcoach-2025-01-15-2.log
    └── ...                           ← 最新
```

每行格式：`yyyy-MM-dd HH:mm:ss.SSS | LEVEL | TAG | MESSAGE`，例：

```
2025-01-15 12:34:56.123 | I | JS/UserManager      | login success uid=u_abc nickname=张三
2025-01-15 12:34:56.234 | D | JS/Nav              | route from=Login to=Home
2025-01-15 12:34:57.001 | I | PoseDetectorModule  | start detector model=yolov8n
2025-01-15 12:34:57.005 | I | PoseCameraView      | open camera lens=BACK
2025-01-15 12:34:57.087 | I | TtsModule           | speak count=1 lang=zh-CN
2025-01-15 12:34:58.500 | E | JS/Http             | api error url=/api/training/save code=4001 msg="积分不足"
```

**RN/JS 与 Native 日志在同一份文件按时序穿插**——这是设计目标，方便 grep 上下文。

筛选技巧：
- 看用户操作链路：`grep -E ' \| (JS/Nav|JS/Click) ' fitcoach-*.log`
- 看接口失败：`grep -E ' \| E \| JS/Http ' fitcoach-*.log`
- 看姿态/相机异常：`grep -E ' \| (PoseDetectorModule|PoseCameraView|PoseCameraController) ' fitcoach-*.log`
- 看 TTS：`grep -E ' \| TtsModule ' fitcoach-*.log`

### 4.2 任务一直 PENDING

可能原因 → 排查动作：

| 现象 | 原因 | 排查/修复 |
|------|------|----------|
| 客户端永远不来 pending | App 没冷启过 / 用户已退出登录 | logcat 看 `LogPullScheduler` 是否 ENQUEUE；登录态：SP 中是否有 `fitcoach.logger.token` |
| 客户端来了 pending 但没命中（list 还 PENDING） | uid 不匹配 | server 日志 `LogPullService.claimNextPending` 入参 uid vs 任务行 uid |
| 客户端命中后没上传（变 UPLOADING 后回滚） | 网络断 / zip 打包失败 | logcat `FCLog/Worker E ...`；5min 后会被 scheduler 回滚成 PENDING 重派 |

### 4.3 任务 FAILED_TERMINAL

服务端 `failReason` 字段会写入终端原因：

- `7307 上传重试次数已达上限` → 看 `retryCount` 字段（最大 3）；通常是网络持续异常或服务端持续 7316 落盘失败
- `7312 文件过大` → 客户端 zip 超 50MB；说明日志体积异常，需要排查是否有日志风暴（某个 tag 在循环里疯狂打）
- `7321 任务已过期` → 客户端在 24h 内没成功上传过；用户长期不开 App

### 4.4 admin 下载 7305 / 7306

- `7305 尚未上传` → admin 工具页只有 UPLOADED 行的"下载"按钮可用；如果手动调 URL 触发，会拿到这个错
- `7306 文件已清理` → 任务超过 7 天，scheduler 已删盘但任务记录还在；建议直接 DELETE 任务

### 4.5 服务端 multipart 413

如果客户端上传被 nginx/Tomcat 截 413，需要同时检查：
1. nginx `client_max_body_size 60m;`（或更大）
2. Spring `spring.servlet.multipart.max-file-size: 60MB / max-request-size: 60MB`
3. Tomcat `server.tomcat.max-swallow-size`（默认 2MB，但 multipart 模式下按上面两项走，一般不用动）

### 4.6 同账号多设备同时登录

`LogPullService.claimNextPending`（被 `/api/client/poll` 通过 `LogPullContribution` 调用）用 PESSIMISTIC_WRITE 行锁，同一 uid 同一时间只有一个设备能拿到任务。其他设备会拿到空 `logTask` → 客户端不 retry，下次 120s 再来。
**结果：哪台设备先轮询到就哪台上传**——这是有意行为，避免同一份日志被两台设备各传一次。

如果业务上想"两台设备日志都要"，需要在 admin 创建任务时点两次（第二次会被 7304 拦下，需要等第一次 UPLOADED 后再创建）。当前需求场景下没必要。

## 5. 验证 checklist（联调期）

按照下面顺序走一遍，全绿即闭环健康：

1. **Server 启动健康**
   - `mvn -pl fitcoach-app spring-boot:run` 启动后看到 `LogTaskScheduler started`
   - GET `/api/admin/logs/tasks?uid=test-not-exist&page=1` 应返 `{code:0, data:{records:[],total:0}}`

2. **AdminManager 创建任务**
   - 浏览器打开 `/tools/logs` → 输入真实在线用户的 uid → 创建
   - 列表立刻看到 PENDING 行 + createdBy 是当前 admin 账号

3. **客户端轮询命中**
   - 客户端 App 处于前台或后台均可（WorkManager 会跑）
   - 等 ≤120s，看到任务从 PENDING → UPLOADED（中间可能瞬过 ASSIGNED/UPLOADING）

4. **下载 zip 可读**
   - admin 列表点"下载" → 浏览器拿到 `fitcoach_log_{uid}_{taskId}.zip`
   - 解压看到 `logs/fitcoach-*.log` 文件，内容包含 RN/JS 行（tag 以 `JS/` 开头）和 Native 行

5. **删除任务**
   - admin 点"删除" → 确认 → 列表消失
   - 服务端 `${UPLOAD_BASE_DIR}/logs/{uid}/{taskId}_*.zip` 文件不存在

6. **过期/清理**（可选，长期观察）
   - 24h 后未完成的 PENDING 自动 EXPIRED
   - 7 天后 UPLOADED 文件自动删盘（任务记录也变 EXPIRED）

## 6. 后续可演进点（非本期）

- **iOS 端补齐** — 当前仅 Android Native 实现；iOS 需要把 `FileLogWriter / LogPackager / LogPullWorker` 各用 Swift 复刻一遍，bridge 名字保持 `FCLogger` 不变，JS 层无需改动。
- **OSS/对象存储** — 当前 zip 落本地磁盘；切 OSS 时需改 `LogStorageService` 把 `Files.write` 换成 OSS SDK，下载接口可改 302 跳转 OSS 预签名 URL。
- **服务端解压预览** — admin 端可加个 "在线浏览前 1000 行" 接口，避免每次都要下载完才能看。
- **结构化日志** — 当前每行是纯文本；如需机器分析（如统计 7xxx 错误码分布），可改成 JSON Lines 格式，在打包时同时输出 `.log` 和 `.jsonl`。
