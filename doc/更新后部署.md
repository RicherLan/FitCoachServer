# 更新后部署

## 日常只执行这一条

```bash
cd /opt/fitcoach/FitCoachServer && bash shell/update.sh
```

**无论有没有SQL变更，都用同一条命令，不需要手动挑SQL、备份或删表。** 脚本每次先`git pull --ff-only`，重新加载拉取后的脚本，再检查并应用该版本登记的迁移，整个过程不再二次拉取不同代码。

服务器第一次还没有`update.sh`时，用下面这一条获取并运行；以后用上面的命令即可：

```bash
cd /opt/fitcoach/FitCoachServer && git pull --ff-only && bash shell/update.sh
```

适用于已有生产数据库、已有app容器的更新；首次空库初始化仍参考[DEPLOY.md](DEPLOY.md)。要求Linux的flock、sha256sum、Git、Docker Compose、curl可用，.env.prod已配置；容器名称沿用本项目生产Compose。运行用户需能写`/data/fitcoach/backup`，或用`FITCOACH_BACKUP_DIR`指定备份目录。更新期间停止app写入，会有维护窗口；同一个数据库如另有写入实例，须先一并停写。不要同时运行旧deploy.sh或手工改库。

## 脚本自动做什么

1. 获取本机部署锁，检查受跟踪文件未修改，拉取代码；失败立即停止。
2. 读取`fitcoach-app/src/main/resources/sql/migrations.list`及数据库迁移记录，检查本次是否有待执行SQL。
3. 保留当前运行镜像为`fitcoach-server:before-update-时间戳-进程号`，构建新镜像。构建失败不会停旧应用。
4. 停止app，备份完整数据库到`/data/fitcoach/backup/`。即使没有新SQL也备份；失败不会执行迁移或启动新版本。未完成备份保留`.partial`后缀。
5. 顺序执行待应用SQL，记录文件SHA256、STARTED/APPLIED状态、时间和是否接管已有迁移；不执行未列入清单的历史修复SQL。
6. 强制`JPA_DDL_AUTO=validate`启动app/nginx，不重建业务表、不停止MySQL、不删除数据卷。
7. 重新加载Nginx以更新app上游地址，从实际映射的HTTPS端口检查`/api/auth/ping`的业务code=0、data=pong，成功后打印版本及备份位置。检查使用真实域名/SNI、连接127.0.0.1且验证TLS证书，避免HTTP跳转导致误判；默认域名migofitai.com，可通过FITCOACH_HEALTH_HOST指定。

迁移记录表为`fitcoach_schema_migration`，由脚本在备份之后建立。记录成功的SQL下次跳过；已发布SQL校验值改变、有STARTED未完成记录，或数据库有当前清单未登记的版本时，脚本停止，避免重复DDL和隐式降级。镜像和数据库备份不自动删除，由运维按保留策略清理。

## 已经手工执行过SQL怎么办

首次使用脚本会核查实际结构，不要求你再手动执行：

| 迁移 | 自动判断 |
|---|---|
| `20260922_membership_entitlement.sql` | 没有表则创建并初始化基线；已有表先检查列类型、唯一键和用户索引，再核查历史会员是否已有权益记录。完整则登记已应用；缺少基线则执行原SQL补齐，不覆盖已有权益；结构不符则停止 |
| `20260922_ai_training_summary.sql` | training_record两列和索引均不存在则执行；全部定义匹配则登记已应用；部分存在/类型或索引不符则停止 |
| `20260923_entitlement_order_collation.sql` | 对齐membership_entitlement.order_id与payment_order.order_id的排序规则；一致则跳过，不一致才ALTER权益表关联列，保留数据 |

这些迁移不删除payment_order。非常旧的支付结构（如plan_code/plan_snapshot_name旧列或缺refund_order）不在这两份迁移的覆盖范围；需要补保留数据的专项SQL，不采用删表或临时JPA update。

遇到失败看脚本最后输出：构建前失败不影响旧服务；停写之后失败会保持app停止，不自动回滚数据库或启动可能不兼容的旧镜像。MySQL DDL可能隐式提交，不能简单清空迁移记录重跑。需根据日志、备份、实际结构修复，再将确认完成的记录校正。不要执行DROP TABLE处理迁移失败。

## 后续开发者新增迁移

- 新增SQL文件，按顺序加入`sql/migrations.list`；名称格式`YYYYMMDD_description.sql`，不要修改已应用的历史文件。
- 在`sql/prechecks/`增加同名只读检查SQL，仅返回一行PENDING、APPLIED或CONFLICT；检查必须同时用于执行前判断和执行后验证，覆盖前置条件及实际结构/数据。
- 不使用清单自动扫描目录。特殊数据修复只有经过明确登记与检查才会在更新时执行。
- 验证：`bash -n shell/update.sh`、`python3 shell/tests/test_update.py`。本机编排回归使用mock Git/Docker/MySQL，不替代真实MySQL集成验证。

`deploy.sh`保留首次部署和日志/状态/手动回滚等旧入口，但不负责SQL迁移；日常发布统一使用`update.sh`。本次开发没有执行服务器更新或数据库迁移。

## 版本变更记录

### 2026-09-22：退款与会员权益账本升级

新增 `membership_entitlement` 表，按订单保存天数快照及退款状态；全额退款重算剩余权益，其他订单/赠送不受整账户撤销影响；部分退款保留原权益。用户行锁保证并发激活/退款串行；撤销先到时以订单墓碑防后续激活。已退款订单由定时任务补偿遗漏的权益事件。

旧会员到期时间以 LEGACY 基线原样保留。旧订单没有当时的天数/赠送拆分，不能用当前套餐配置猜测；旧订单退款需要管理员根据实际历史核对基线，新代码不会为此直接撤销整个账户。新下单订单已保存权益快照，不受此限制。更新脚本在停写窗口检查并执行，迁移记录成功后不再重跑；已有账本但缺基线时只补缺少的基线，不覆盖已有权益记录。

退款请求现在先独立提交退款号，再调用通道。超时保留 PENDING 和金额预占；后台订单详情可用原退款号重试。明确拒绝保存 FAILED；退款回调按商户退款号查找并校验订单/金额，支持回调早到。Apple 不再允许管理员无凭据直接标记退款，必须通过已验签的平台通知。Google 按用户要求未接入。

Admin `/assets/` 已改为读后台静态目录，部署后重新加载 Nginx。上述命令是部署说明，本次本地开发没有执行服务器部署或数据库操作。

### 2026-09-22：AI 训练结果与历史对比

更新脚本在发布新版 Server / RN 前自动检查并执行 `fitcoach-app/src/main/resources/sql/20260922_ai_training_summary.sql`（一次性 ALTER；已应用则跳过）。新增 `training_record.ai_summary_json`、`ai_exercise_key` 及按用户/动作/日期索引。摘要可空，旧手动记录与旧客户端兼容。不要在未迁移的生产库直接启动新服务。

- POST/PUT `/api/training-record` 支持 `aiSummary`：schemaVersion=1、exerciseKey、model、countMode、sets。每组保存 recognizedReps、confirmedReps、activeMs、meanRepMs、rangeDegrees、validFrameRatio、feedback。仅摘要入库，不接收原始视频/骨架流。
- GET `/api/training-record/ai-history?exerciseKey=SQUAT`：鉴权用户本人最近20条，不允许客户端指定用户。
- 嵌套 Bean Validation 限制数量、范围、模型；AI摘要的动作/组数/确认次数必须与日志一致。AI测量属于客户端数据，不作为支付、会员权限或医疗评分依据。
- 启动Seeder补齐 `SQUAT` / `WIDE_PUSH_UP` / `LUNGE` 三个记录模板，已有模板不覆盖。其余旧AI key在客户端/校验器明确映射到记录字典。
- 发布顺序：备份/两份20260922迁移 → Server → Admin → RN。新 RN 的训练入口依赖 `/api/exercise/start`，旧 Server 不支持时不会绕过校验开始训练。
- 本地测试覆盖：AI摘要JSON往返、嵌套约束与用户修正的一致性；不代表已完成生产数据库迁移或双端真机验收。

### 2026-09-23：修复HTTPS健康检查与权益订单排序规则

用户服务器已走到[7/7]，前两份迁移成功后，旧脚本因HTTP入口301跳转而无法匹配pong；同时退款补偿查询出现0900_ai_ci/unicode_ci混合排序规则错误。

- update.sh改用Nginx实际HTTPS映射端口，curl --resolve指定本机IP及真实域名/SNI，不关闭证书验证；重载Nginx刷新app上游地址，失败打印最后响应。
- 新增20260923_entitlement_order_collation.sql，按payment_order.order_id的实际utf8mb4排序规则调整权益表对应列，不改历史SQL及其校验和，不清除迁移记录。
- 恢复时仍执行本文开头同一条更新命令。脚本跳过前两份成功记录，备份后只执行新迁移；原app停止的容器可以由更新流程重新启动。不要手工删除STARTED/APPLIED记录。
- Compose的version obsolete是兼容性提示，不是此次失败根因。本轮本机没有真实MySQL/Docker集成环境，脚本回归用模拟命令覆盖HTTPS/重载/失败后追加迁移恢复。
