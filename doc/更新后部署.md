# 更新后部署

> 本文是已有数据库的增量更新流程。每次更新影响哪些表，由该版本的实际 SQL 决定，不能固定删除或重建某张表。
> **旧文中的删除 payment_order、临时开启 JPA update 已移除，不要再执行。** 未正式上线也不代表数据库可以直接清空。
> 本文命令在服务器上执行；本次修订没有连接服务器或执行数据库操作。完整部署背景见 [DEPLOY.md](DEPLOY.md)。

## 一、所有更新都先拉取代码

无论有没有 SQL 变更，都先执行这一步，成功后再根据拉取后的代码、SQL 和部署说明判断后续操作：

```bash
cd /opt/fitcoach/FitCoachServer && git pull --ff-only
```

如果拉取失败，先处理失败原因，不继续部署。不要在核查迁移和部署之间再次拉取不同版本的代码。

## 二、根据更新后的版本判断是否需要迁移

- 没有待执行的数据库迁移、且现有结构符合新代码：执行下面的普通部署命令。
- 有新增表/列/索引或数据迁移：检查当前结构、选择**尚未执行**的增量 SQL，再按第三节备份、执行和部署。
- 生产保持 `JPA_DDL_AUTO=validate`，不要用 Hibernate 自动改表来掩盖遗漏的迁移。
- 当前没有自动迁移版本账本，不要遍历 SQL 目录全部执行；其中也有历史数据修复脚本，不是每次发布必跑。

无待执行迁移时，在完成第一节拉取后部署：

```bash
cd /opt/fitcoach/FitCoachServer && bash shell/deploy.sh
```

当前已提供的两份结构迁移：

| SQL文件（位于fitcoach-app/src/main/resources/sql/） | 实际影响 | 执行条件 |
|---|---|---|
| `20260922_membership_entitlement.sql` | 新建membership_entitlement；读取user_membership初始化历史权益基线 | 尚未完成权益账本迁移时执行；已有表应检查结构和基线迁移记录，不能仅凭表存在/为空决定重跑 |
| `20260922_ai_training_summary.sql` | training_record新增ai_summary_json、ai_exercise_key及idx_training_record_ai_history索引 | 两列和索引均未创建时执行一次；全部已存在则核对定义后跳过；部分存在需针对实际结构补迁移 |

这两份SQL**均不删除payment_order，也不负责历史payment_order旧字段到通用商品字段的迁移**。如果数据库仍是更早版本（如只有plan_code/plan_snapshot_name或没有refund_order），先提供实际SHOW CREATE TABLE结果，按实体核对并补保留数据的专项SQL，不套用删表方案。

在服务器上只读检查当前结构：

```bash
cd /opt/fitcoach/FitCoachServer
docker exec fitcoach-mysql-prod sh -ec '
  export MYSQL_PWD="$MYSQL_ROOT_PASSWORD"
  exec mysql -uroot "${MYSQL_DATABASE:-fitcoach}" -e "
    SELECT TABLE_NAME FROM information_schema.TABLES
      WHERE TABLE_SCHEMA=DATABASE()
      AND TABLE_NAME IN (\"membership_entitlement\", \"user_membership\", \"training_record\", \"payment_order\", \"refund_order\");
    SHOW COLUMNS FROM training_record;
    SHOW INDEX FROM training_record;
    SHOW CREATE TABLE payment_order;
  "
'
```

已有membership_entitlement时还需检查它的SHOW CREATE TABLE及历史迁移记录。结构检查不等于确认所有数据迁移已执行，不要通过反复跑SQL来试探。

## 三、有数据库迁移时的部署模板

前置条件：已完成第一节拉取，并按第二节核查本次版本所需的迁移。下面只执行迁移和部署，不重复拉取代码。

下面示例列出两份20260922迁移，**仅适用于它们都尚未执行且现有库符合前置条件的情况**。按本次版本和上面的核查结果编辑 `migration_files`：只保留实际需要的SQL，未来修改其他表时换成对应的新SQL，命令本身不绑定表名。

备份前进入维护窗口，停止所有向该库写入的应用/后台任务；下面的`stop app`只覆盖当前Compose中的服务端实例。不要停止MySQL或删除数据卷。

```bash
bash <<'BASH'
set -euo pipefail
cd /opt/fitcoach/FitCoachServer

# 按本次版本选择尚未执行的SQL；不要自动执行目录下全部SQL。
migration_files=(
  fitcoach-app/src/main/resources/sql/20260922_membership_entitlement.sql
  fitcoach-app/src/main/resources/sql/20260922_ai_training_summary.sql
)
for sql_file in "${migration_files[@]}"; do
  test -s "$sql_file" || { echo "SQL文件缺失：$sql_file" >&2; exit 1; }
done

# 先构建，构建失败时不影响旧服务和数据库。
docker compose --env-file .env.prod -f shell/docker-compose.prod.yml build app

# 停止旧应用写入，数据库保持运行。
docker compose --env-file .env.prod -f shell/docker-compose.prod.yml stop app
trap 'echo "更新未完成：检查备份和SQL执行结果，不要自动重跑迁移或切回不兼容的旧应用。" >&2' ERR

# 数据库密码在容器内读取，不依赖宿主机导出MYSQL_ROOT_PASSWORD。
umask 077
mkdir -p /data/fitcoach/backup
backup_file="/data/fitcoach/backup/fitcoach-$(date +%Y%m%d-%H%M%S)-$$.sql"
docker exec fitcoach-mysql-prod sh -ec '
  export MYSQL_PWD="$MYSQL_ROOT_PASSWORD"
  exec mysqldump -uroot --single-transaction --routines --events --triggers     --no-tablespaces --set-gtid-purged=OFF "${MYSQL_DATABASE:-fitcoach}"
' > "$backup_file"
test -s "$backup_file"
echo "备份完成：$backup_file"

# 按明确选定的顺序执行；不加--force，任一SQL失败立即停止。
for sql_file in "${migration_files[@]}"; do
  echo "执行迁移：$sql_file"
  docker exec -i fitcoach-mysql-prod sh -ec '
    export MYSQL_PWD="$MYSQL_ROOT_PASSWORD"
    exec mysql -uroot "${MYSQL_DATABASE:-fitcoach}"
  ' < "$sql_file"
done

# 前面已经构建过当前代码；保持JPA_DDL_AUTO=validate。
bash shell/deploy.sh --skip-build
BASH
```

注意：MySQL DDL可能隐式提交，SQL失败不代表已执行部分会自动回滚。发生错误先核对实际结构，再决定修复或从已验证的备份恢复。deploy.sh的镜像回滚不回滚数据库，涉及不兼容结构变化时要单独准备回滚方案。本模板预构建后使用skip-build启动，不能依赖deploy.sh自动备份得到更新前镜像；如需保留旧镜像，应在build前额外记录旧镜像ID并打独立回滚标签。

## 四、部署后验证

```bash
curl --fail --show-error https://migofitai.com/api/auth/ping
docker logs fitcoach-app-prod --tail 100
```

按本次SQL检查其影响的表/列/索引；本轮应检查membership_entitlement和training_record，不能始终只检查payment_order。接口响应应为业务成功且data为pong，并确认日志无Schema-validation失败，再验证会员/训练记录等对应功能。

如果JPA校验失败，按日志指出的实际差异补增量SQL；不要删表，也不要直接切换update后重启。仅健康接口能访问不等于迁移和业务验收完成。

## 五、版本变更记录

### 2026-09-22：退款与会员权益账本升级

新增 `membership_entitlement` 表，按订单保存天数快照及退款状态；全额退款重算剩余权益，其他订单/赠送不受整账户撤销影响；部分退款保留原权益。用户行锁保证并发激活/退款串行；撤销先到时以订单墓碑防后续激活。已退款订单由定时任务补偿遗漏的权益事件。

旧会员到期时间以 LEGACY 基线原样保留。旧订单没有当时的天数/赠送拆分，不能用当前套餐配置猜测；旧订单退款需要管理员根据实际历史核对基线，新代码不会为此直接撤销整个账户。新下单订单已保存权益快照，不受此限制。该SQL包含历史会员基线初始化，应只在确认尚未迁移的维护窗口执行；不能因为CREATE TABLE使用IF NOT EXISTS就把整份SQL当作每次部署都要运行。

退款请求现在先独立提交退款号，再调用通道。超时保留 PENDING 和金额预占；后台订单详情可用原退款号重试。明确拒绝保存 FAILED；退款回调按商户退款号查找并校验订单/金额，支持回调早到。Apple 不再允许管理员无凭据直接标记退款，必须通过已验签的平台通知。Google 按用户要求未接入。

Admin `/assets/` 已改为读后台静态目录，部署后重新加载 Nginx。上述命令是部署说明，本次本地开发没有执行服务器部署或数据库操作。

### 2026-09-22：AI 训练结果与历史对比

在发布新版 Server / RN 之前执行 `fitcoach-app/src/main/resources/sql/20260922_ai_training_summary.sql`（一次性 ALTER；先确认列尚不存在；先备份数据库）。新增 `training_record.ai_summary_json`、`ai_exercise_key` 及按用户/动作/日期索引。摘要可空，旧手动记录与旧客户端兼容。不要在未迁移的生产库直接启动新服务。

- POST/PUT `/api/training-record` 支持 `aiSummary`：schemaVersion=1、exerciseKey、model、countMode、sets。每组保存 recognizedReps、confirmedReps、activeMs、meanRepMs、rangeDegrees、validFrameRatio、feedback。仅摘要入库，不接收原始视频/骨架流。
- GET `/api/training-record/ai-history?exerciseKey=SQUAT`：鉴权用户本人最近20条，不允许客户端指定用户。
- 嵌套 Bean Validation 限制数量、范围、模型；AI摘要的动作/组数/确认次数必须与日志一致。AI测量属于客户端数据，不作为支付、会员权限或医疗评分依据。
- 启动Seeder补齐 `SQUAT` / `WIDE_PUSH_UP` / `LUNGE` 三个记录模板，已有模板不覆盖。其余旧AI key在客户端/校验器明确映射到记录字典。
- 发布顺序：备份/两份20260922迁移 → Server → Admin → RN。新 RN 的训练入口依赖 `/api/exercise/start`，旧 Server 不支持时不会绕过校验开始训练。
- 本地测试覆盖：AI摘要JSON往返、嵌套约束与用户修正的一致性；不代表已完成生产数据库迁移或双端真机验收。
