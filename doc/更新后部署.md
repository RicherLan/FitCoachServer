# 更新后部署

> 本次代码有 **数据库表结构变更**，普通 `deploy.sh` 不会自动改表，需按本文处理。
> 完整部署背景见 [`DEPLOY.md`](DEPLOY.md)，本文只讲「这次更新」怎么上。

## 本次表结构变更

- `payment_order`：`plan_code`→`product_code`、`plan_snapshot_name`→`product_name`，新增 `product_type`
- 新增表 `refund_order`（退款流水）

> 下面默认 **未正式上线、支付订单无重要数据**，采用「重建 payment_order + JPA 自动建表」最省事方案。
> 若需保留旧订单数据，见文末「附：保留数据」。

---

## 部署步骤（全部在服务器上执行）

```bash
cd /opt/fitcoach/FitCoachServer

# 1) 拉最新代码
git pull

# 2) 备份数据库（保险，无论是否保留数据都先备份）
mkdir -p /data/fitcoach/backup
docker exec fitcoach-mysql-prod sh -c \
  'mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" --single-transaction fitcoach' \
  > /data/fitcoach/backup/fitcoach-$(date +%Y%m%d-%H%M%S).sql

# 3) 删除旧 payment_order（未上线无数据；refund_order 是新表不用管，JPA 会建）
docker exec -it fitcoach-mysql-prod \
  mysql -u root -p"$MYSQL_ROOT_PASSWORD" fitcoach \
  -e "DROP TABLE IF EXISTS payment_order;"

# 4) 临时开启 JPA 自动建表：编辑 .env.prod，把
#      JPA_DDL_AUTO=validate  改成  JPA_DDL_AUTO=update
vim .env.prod

# 5) 部署（build + 重启，启动时 Hibernate 会按新实体建 payment_order + refund_order）
bash shell/deploy.sh

# 6) 建表成功后改回严格模式：.env.prod 把 JPA_DDL_AUTO 改回 validate
vim .env.prod
bash shell/deploy.sh --skip-build      # 仅重启生效，不重新 build
```

## 说明 & 注意

- **为什么能直接 drop `payment_order`**：`refund_order`、`user_membership` 均为逻辑关联（无外键 FK 约束），drop 不会被阻塞。
- **务必改回 `validate`**：`update` 长期开启有「误改表结构」风险，仅建表时临时用。
- 若 `deploy.sh` 因 `validate` 报 schema 校验错启动失败，说明第 3~5 步没做全，回头补即可。

## 附：保留数据（可选，仅当 payment_order 有需保留的订单）

不执行第 3 步 drop，改为手动迁移（保持 `validate`，跳过第 4/6 步的 update）：

```sql
-- 加新列
ALTER TABLE payment_order
  ADD COLUMN product_type VARCHAR(32),
  ADD COLUMN product_code VARCHAR(64),
  ADD COLUMN product_name VARCHAR(128);

-- 迁移旧值（历史订单都是会员）
UPDATE payment_order SET
  product_type = 'MEMBERSHIP',
  product_code = plan_code,
  product_name = plan_snapshot_name;

-- 置非空 + 删旧列
ALTER TABLE payment_order
  MODIFY product_type VARCHAR(32) NOT NULL,
  MODIFY product_code VARCHAR(64) NOT NULL,
  MODIFY product_name VARCHAR(128) NOT NULL,
  DROP COLUMN plan_code,
  DROP COLUMN plan_snapshot_name;
```

`refund_order` 表仍需建（临时 `update` 跑一次，或手动按实体建表）。
# 2026-09-22：退款与会员权益账本升级

部署这次版本前，先在服务器仓库执行增量 SQL（会提示输入数据库 root 密码，不把密码写进 shell 历史）：

```bash
cd /opt/fitcoach/FitCoachServer
git pull --ff-only
docker cp fitcoach-app/src/main/resources/sql/20260922_membership_entitlement.sql fitcoach-mysql-prod:/tmp/20260922_membership_entitlement.sql
docker exec -it fitcoach-mysql-prod mysql -uroot -p fitcoach -e 'source /tmp/20260922_membership_entitlement.sql'
bash shell/deploy.sh
```

新增 `membership_entitlement` 表，按订单保存天数快照及退款状态；全额退款重算剩余权益，其他订单/赠送不受整账户撤销影响；部分退款保留原权益。用户行锁保证并发激活/退款串行；撤销先到时以订单墓碑防后续激活。已退款订单由定时任务补偿遗漏的权益事件。

旧会员到期时间以 LEGACY 基线原样保留。旧订单没有当时的天数/赠送拆分，不能用当前套餐配置猜测；旧订单退款需要管理员根据实际历史核对基线，新代码不会为此直接撤销整个账户。新下单订单已保存权益快照，不受此限制。SQL 可重跑但应在维护窗口、旧服务停止写订单时首次执行。

退款请求现在先独立提交退款号，再调用通道。超时保留 PENDING 和金额预占；后台订单详情可用原退款号重试。明确拒绝保存 FAILED；退款回调按商户退款号查找并校验订单/金额，支持回调早到。Apple 不再允许管理员无凭据直接标记退款，必须通过已验签的平台通知。Google 按用户要求未接入。

Admin `/assets/` 已改为读后台静态目录，部署后重新加载 Nginx。上述命令是部署说明，本次本地开发没有执行服务器部署或数据库操作。

### 2026-09-22：AI 训练结果与历史对比

在发布新版 Server / RN 之前执行 `fitcoach-app/src/main/resources/sql/20260922_ai_training_summary.sql`（一次性 ALTER；先确认列尚不存在；先备份数据库）。新增 `training_record.ai_summary_json`、`ai_exercise_key` 及按用户/动作/日期索引。摘要可空，旧手动记录与旧客户端兼容。不要在未迁移的生产库直接启动新服务。

- POST/PUT `/api/training-record` 支持 `aiSummary`：schemaVersion=1、exerciseKey、model、countMode、sets。每组保存 recognizedReps、confirmedReps、activeMs、meanRepMs、rangeDegrees、validFrameRatio、feedback。仅摘要入库，不接收原始视频/骨架流。
- GET `/api/training-record/ai-history?exerciseKey=SQUAT`：鉴权用户本人最近20条，不允许客户端指定用户。
- 嵌套 Bean Validation 限制数量、范围、模型；AI摘要的动作/组数/确认次数必须与日志一致。AI测量属于客户端数据，不作为支付、会员权限或医疗评分依据。
- 启动Seeder补齐 `SQUAT` / `WIDE_PUSH_UP` / `LUNGE` 三个记录模板，已有模板不覆盖。其余旧AI key在客户端/校验器明确映射到记录字典。
- 发布顺序：备份/两份20260922迁移 → Server → Admin → RN。新 RN 的训练入口依赖 `/api/exercise/start`，旧 Server 不支持时不会绕过校验开始训练。
- 本地测试覆盖：AI摘要JSON往返、嵌套约束与用户修正的一致性；不代表已完成生产数据库迁移或双端真机验收。
