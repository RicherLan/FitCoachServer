# FitCoach Server — 后端技术文档

## 一、项目概述

FitCoach Server 是 FitCoach AI 健身教练的后端服务，基于 Spring Boot 构建，为 Android 客户端提供用户认证、数据存储等 API 服务。

### 核心功能

- **微信登录**：接收客户端微信授权码，换取 access_token 并获取用户信息，生成 JWT 返回
- **用户管理**：用户注册/查询、登录状态管理
- **系统配置**：微信 AppId/AppSecret 等敏感配置存储在数据库中，可通过后台管理

### 5.4 客户端版本/设备协议（X-Client-* + X-Device-Id 六件套）

> 实现：[`ClientInfoInterceptor`](fitcoach-common/src/main/java/com/lanprojects/fitcoach/common/client/ClientInfoInterceptor.java) + [`ClientContext`](fitcoach-common/src/main/java/com/lanprojects/fitcoach/common/client/ClientContext.java) + [`ClientVersionInfo`](fitcoach-common/src/main/java/com/lanprojects/fitcoach/common/client/ClientVersionInfo.java)
>
> RN 端实现：`src/common/clientInfo/clientInfo.ts` + `src/common/clientInfo/deviceIdProvider.ts`
>
> 注册：[`WebConfig`](fitcoach-app/src/main/java/com/lanprojects/fitcoach/config/WebConfig.java) `/api/**`（排除 `/api/admin/**`）

#### 协议（每个客户端→server 请求都带）

| Header | 类型 | 例 | 用途 |
|---|---|---|---|
| `X-Client-Platform` | string | `android` / `ios` | 区分平台 |
| `X-Client-Native-Version-Code` | int | `1002003` | 安装包版本（应用市场上架的） |
| `X-Client-Native-Version-Name` | string | `"1.2.3"` | 同上，可读 |
| `X-Client-Bundle-Version-Code` | int | `1002005` | 当前运行的 JS bundle 版本（OTA 后会与 native 不同） |
| `X-Client-Bundle-Version-Name` | string | `"1.2.5"` | 同上，可读 |
| `X-Device-Id` | string | `"a1b2…uuid"` / `"unknown"` | 设备唯一标识（首次安装生成 UUIDv4 持久化） |

**编码规则**：`MAJOR*1_000_000 + MINOR*1_000 + PATCH`（每段 0-999）。例 `1.2.3 → 1_002_003`。RN 客户端 / Android Kotlin / iOS ObjC / Server Java 算法严格一致。

**两层版本设计要点**：
- `nativeVersion` ← gradle / Info.plist，改动场景：加 native 依赖、改原生 Module。判断"用户的安装包是否支持某个新 native 接口"。
- `bundleVersion` ← RN `package.json` 的 `version`，改动场景：纯 JS/TS 改动。判断"当前运行的代码是否实现了某个新业务契约"。未来接 OTA 后可静默推送。

**deviceId 设计要点**：
- RN 端首次启动生成 UUIDv4 落 AsyncStorage（key=`fitcoach.device_id`），后续启动复用；
- 不依赖 IMEI / Android-ID / IDFA / WiFi-MAC 等系统标识 —— 无需任何隐私敏感权限，天然合规；
- 卸载重装会得到新 ID（这是预期；账号-设备绑定由 server 端在登录时把当前 deviceId 写入 session 表，跨设备识别交给 server）；
- App 启动早期 `await initDeviceId()`（`App.tsx` 第一行）保证首批请求 Header 携带真实值；
- 极端兜底窗口（init 异常）下值为 `"unknown"`，业务侧需要严格判断时用 `ClientContext.get().hasDeviceId()`。

#### 业务侧使用

```java
import com.lanprojects.fitcoach.common.client.ClientContext;

// 1) 直接读 versionCode 做条件判断（最常用）
if (ClientContext.bundleVersionCode() >= 1_001_000) {
    // 1.1.0 起支持新接口契约，走新逻辑
}

// 2) 平台分流
if (ClientContext.isIos()) { ... }

// 3) deviceId（单设备登录互踢、风控）
String deviceId = ClientContext.deviceId();
if (ClientContext.get().hasDeviceId()) {
    // 拿到了真实 UUID，可以做绑定/互踢判断
}

// 4) 拿全量信息
ClientVersionInfo info = ClientContext.get();
if (info.isEmpty()) {
    // admin 后台 / Postman / 老版本无埋点客户端
}
```

#### 缺失语义

- admin 后台、Postman 调试请求 → `ClientContext.get()` 返回 `EMPTY`，业务自己判 `isEmpty()` 即可。
- Header 存在但格式异常（如 versionCode 不是数字）→ 静默降级为 0，不打 ERROR 日志。
- `X-Device-Id` 缺失（admin/Postman）或为 `"unknown"`（客户端启动早期）→ 业务用 `hasDeviceId()` 双判，避免把"未知设备"当成"另一台设备"误处理。

### 5.5 单设备登录互踢

> 复用 5.4 deviceId 协议 + JWT `sid` claim 实现"同账号只允许一台设备在线"，新设备登录会把老设备挤下线。
>
> 核心权威：Server 端 `AuthService.parseAndAssertSession()` 一处校验，所有鉴权请求自动覆盖。

#### 数据模型

`fitcoach-login` `User` 实体新增三个字段（JPA `ddl-auto=update` 自动建列）：

| 字段 | 含义 |
|---|---|
| `current_session_id` | 当前生效会话 ID（每次客户端登录翻新） |
| `current_device_id` | 当前生效设备的 deviceId（审计/排障用） |
| `current_login_at` | 当前会话登录时间 |

#### 链路全景

```
  ┌─────────────────┐ 1. POST /api/auth/login (header: X-Device-Id=A)
  │  设备 A 登录    │──────────────────────────────────────┐
  └─────────────────┘                                       ▼
                                          ┌──────────────────────────────────┐
                                          │ AuthService.rotateSessionForLogin │
                                          │  · hasDeviceId()=true             │
                                          │  · sid_A = UUID()                 │
                                          │  · user.currentSessionId = sid_A  │
                                          └────────────────┬─────────────────┘
                                                           │
                                          access/refresh JWT 都带 claim sid=sid_A
                                                           │
  ┌─────────────────┐ 2. POST /api/auth/login (header: X-Device-Id=B)
  │  设备 B 登录    │──────────────────────────────────────┐
  └─────────────────┘                                       ▼
                                          user.currentSessionId 被覆盖为 sid_B
                                                           │
  ┌─────────────────┐ 3. 设备 A 任意请求(jwt.sid=sid_A) ─→ AuthService.getCurrentUser
  │  设备 A 兜底    │     parseAndAssertSession() 比对 sid_A != sid_B
  └─────────────────┘     → 抛 SESSION_KICKED(1006)
                          ↓
              RN httpClient.ts rawRequest 全局拦截 1006
                          ↓
              setSessionKickedHandler 回调 (RootNavigator 注入)
              · UserManager.logout() 清本地 session
              · ToastAndroid 提示 "账号已在其他设备登录"
              · navigationRef.navigate('Login')
                          ↓
              Native LogPullWorker 下个 120s tick:
              LoggerCredentials.isReady()=false → 静默 skip
```

#### 设计要点

- **JWT `sid` claim**：[`JwtUtils`](fitcoach-login/src/main/java/com/lanprojects/fitcoach/login/util/JwtUtils.java) 签发时加 `sid`，`parsePayload()` 返回 `JwtPayload(uid, sessionId)` record；`parseAndVerify()` 老签名保留兼容历史调用方。
- **校验单点**：所有鉴权链路都过 [`AuthService.getCurrentUser()`](fitcoach-login/src/main/java/com/lanprojects/fitcoach/login/service/AuthService.java) → `parseAndAssertSession()`；包括通用轮询 `/api/client/poll`（自带"被踢即刻发现"能力，无需新建专用通知接口）。
- **何时不参与互踢**：
  - JWT 无 `sid` claim（老 token）→ 跳过校验；
  - 客户端登录时 `hasDeviceId() == false`（admin/Postman/无埋点客户端）→ `rotateSessionForLogin` 不写 `currentSessionId`，`activeSid` 为 null 时跳过比对。
- **refresh 不滚 sid**：`refresh` 沿用 `user.currentSessionId`，旧设备拿旧 refreshToken 也会立刻被同一处校验拦下。
- **零信任原则**：Server 是唯一权威，client 只负责"被踢清理"；不做"主动通知 server 我下线了"。

#### RN 客户端实现

| 文件 | 角色 |
|---|---|
| `src/common/http/httpClient.ts` | `RESULT_CODE_SESSION_KICKED=1006` + `setSessionKickedHandler` + 2s 防抖（`sessionKickedFiring` lock，避免并发请求触发多次 logout） |
| `src/navigation/RootNavigator.tsx` | 注入 handler：`UserManager.logout()` → `ToastAndroid.show(message)` → `navigationRef.navigate('Login')`；当前已在 Login 页则跳过导航 |
| `android/.../logger/pull/LogApiClient.kt` | `LogApiException` 带 `bizCode`，poll/upload 都返回业务码 |
| `android/.../logger/pull/LogPullWorker.kt` | 识别 `bizCode==1006` → `LoggerCredentials.clearAuth()`，避免 Worker 继续无效轮询；下个 tick `isReady()==false` 静默 skip |

#### 错误码对照

| code | 出处 | 客户端动作 |
|---|---|---|
| `1006` SESSION_KICKED | `ResultCode.SESSION_KICKED` | RN：弹 toast + logout + 跳 Login；Native Logger：清凭证 |

## 七、配置管理设计

本项目采用**数据库存储动态配置**的方案，避免敏感信息硬编码。

### 设计原则

1. **敏感配置不入代码库**：微信 AppSecret、JWT 密钥等存在数据库中
2. **支持热更新**：管理员通过后台修改后调用 `SysConfigService.refreshCache()` 即刻生效
3. **内存缓存**：配置读取走内存缓存，不频繁查库
4. **首次启动自动初始化**：`DataInitializer` 在数据库为空时自动插入默认配置

### 读取配置示例

```java
// 在 Service 中注入 SysConfigService
@Autowired
private SysConfigService sysConfigService;

// 读取字符串配置
String appId = sysConfigService.getValue("wechat.app_id");

// 读取整数配置（带默认值）
int expireHours = sysConfigService.getIntValue("jwt.expire_hours", 168);
```
